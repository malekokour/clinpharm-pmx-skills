# Boundaries — work this product deliberately does not cover

The job model describes **167 tasks**. 165 are covered by something that runs. Two are
not, and they are named here rather than left as silence.

A boundary is an owner decision about product scope. It is not a judgment that the work
is unimportant, and it is not a gap waiting to be filled by the next release.

## The two

### Hiring, mentoring and capability building

*Band C · Function leadership and operations · People*

Real professional work, and a large part of what a clinical pharmacology function
actually does. It is outside this product because **there is no evidence pack to
prepare.** Every other task in the model produces or reviews an artifact — a study
report, a label section, a submission summary, an analysis deliverable. This one
produces a developed colleague.

A skill here would either be generic management advice wearing a clinical-pharmacology
label, or a document nobody needed.

### Cross-functional representation

*Band C · Function leadership and operations · Governance*

The deliverable is a person in a room, holding a position, answering questions in real
time, and carrying the accountability for what they say. **There is no artifact for a
skill to produce.**

Note what is *not* on this list: preparing the evidence someone carries into that room
is covered, by several skills. The boundary falls between preparing a position and
holding one.

## Why these two and not more

An earlier pass placed 18 further tasks outside the product. That was wrong, and it was
reversed: in every one of those cases the *work* was real and delegable, and only the
**decision** was not. Preparing the evidence for a decision is a job a skill can do; the
decision itself is refused.

That pattern has a name in this library — a **refuse-boundary skill**. It assembles the
pack, lays out the options and what each rests on, surfaces what is missing, names the
accountable human role, and then declines to conclude. Roughly a dozen tasks work this
way.

So the test for a boundary is not "does a human decide this?" — humans decide most of
it. The test is **"is there an artifact a skill could prepare?"** For these two, there
is not.

## What happens if you ask for one

The router refuses and names the boundary. It does not offer a nearby skill as a
substitute, because a substitute would answer a question you did not ask.

## Revisit trigger

Either row acquires a real evidence pack that a skill could prepare — for example, a
structured capability framework that a review workflow could check work against. At that
point the boundary is wrong and should be reopened with a decision record.

## Where this comes from

Recorded per row in the coverage ledger with `class: boundary` and a stated reason. The
published map shows them alongside every other task, so the count a reader sees is
**167**, not 165 with two quietly removed.
